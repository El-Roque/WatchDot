# Architecture

## Targets and identity

`src/WatchDot.xcodeproj` contains a standalone watchOS app and a WidgetKit launcher extension. There is no iOS app or app-owned Bluetooth/UDP relay. Signing settings are public templates; each installer supplies their own development team and identifiers.

The application entry point is `Sources/WatchDotApp/WatchDotApp.swift`. Shared account, Dot-routing and media helpers live in `Sources/WatchDotCore`. Some account-record compatibility types remain because they are part of the persisted session schema and shared verification code. The obsolete phone application, WatchConnectivity transport, Bluetooth streaming implementation, UDP Swift transport and alternate voice-control app flows are not included.

## Account and call ownership

The Watch starts a device-code OAuth flow only after a user action. Authorization uses HTTPS, bounded polling, PKCE verification and ID-token signature/issuer/audience/time checks. Session data is stored in the app's Keychain. The app verifies the account's primary Dot and routing context before creating a call.

A call generation owns one remote allocation, the native media session and one CallKit call. Cancellation stops local capture promptly and closes the allocation it owns. Ending is idempotent: the UI shows a finishing state while cleanup completes, without another end button.

## Media

CallKit activates the system audio session before low-level networking starts. `WatchRealtimeAudioIO` owns capture/playback and Opus conversion. `WatchTCPTransport` owns Network.framework connections, bounded queues and RFC 4571 framing. The Rust RTC engine owns ICE, DTLS, SRTP, Opus RTP and SCTP events.

Both Xcode configurations use optimized Swift code generation (`-O`), matching the physically accepted build. The audio capture admission mutex only protects bounded state updates; player scheduling and graph resets run on the serial audio owner after releasing that mutex, with cancellation checks around admission.

Capture initially sends muted PCM. Admission requires connected media, open events, an attachment request, a current account and an active call generation. Authenticated remote audio can establish readiness before the attachment HTTP response returns; a successful attachment response is the fallback when no remote audio arrives. The asynchronous account check is fenced by call generation and cancellation. The HTTP result is still validated, and rejection ends the call even if media was admitted earlier. Cleanup waits for any in-flight attachment before releasing the owned allocation. A one-shot first-unmuted-microphone-packet timing marker records local admission without storing audio.

The server may advertise an IPv4 passive ICE-TCP peer while Network.framework presents an IPv6 peer with a translated port. The connection retains its original candidate index and registers the real observed peer tuple with the engine. Candidate attributes and the negotiated DTLS identity are preserved; invented local addresses and unauthenticated forwarding are not used. Each TCP flow owns one exact observed tuple. Checks without an owning socket are treated as loss; media still requires an exact owner.

The paired iPhone can supply system Internet connectivity. It is not running WatchDot code. Native audio/RTC runs on the Watch, and the Mac is not a voice relay.

## UI and resources

The English interface uses the previously accepted circular call action and microphone/end controls, a light timer and adaptive spacing on small displays. Account setup, errors, accessibility labels and the microphone explanation are also in English. System-owned dialogs follow the system language. The main screen provides call, duration, volume, mute and end controls. The waiting sound is generated by `scripts/generate_ringback.py`: one second of two sine waves, followed by the existing three-second playback pause. The generated resource replaces the formerly extracted desktop-client sound.

The launcher extension only displays a bounded-size bitmap in circular/corner positions and opens its containing app. It has no account, networking, microphone or call-control code. Its kind follows the extension bundle identifier, retaining the existing kind when the existing base app identifier is used.

## Diagnostics and privacy

App diagnostics contain fixed stage names, timestamps, counters and error codes. TCP route observations store address families and comparison booleans, not addresses, ports, SDP, credentials, audio or conversation text. Do not publish account containers, OAuth tokens, signing material, raw network captures or device inventories.

Physical validation is distinct from compilation and synthetic tests. `NWPath` interface flags alone do not identify the physical radio path reliably. See `VALIDATION.md` for the confirmed behavior and its limits.
